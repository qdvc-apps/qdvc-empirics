## 1. User request

Today we will be building QDVC Empirics. QDVC Empirics is to be a Mac app built with Swift that supports a researcher performing qualitative data analysis of files.

**CODEBOOK:** The user can define a `CODEBOOK` in line with qualitative data analysis principles.

- A codebook contains an ordered list of `QUESTIONS` instances. Each question has a short label (max. 16 characters), full question text, and data type for the expected answer. Possible data types include free-entry text, select one item (string) from list, or select multiple items (strings) from list. Such a list (of strings) can be set as strictly predefined by the codebook, or not. If not strictly predefined by the codebook, then the researcher can add to it while coding. Each codebook item can also be marked as `mandatory, blocking`, `mandatory, non-blocking`, or `optional`.

- A codebook can be marked as applicable to empirical files AND/OR open codes AND/OR axial codes (see below) and then associated by the researcher with the payload of an empirical file or open code or axial code. Each researcher can then complete the answers to the questions, resulting in a `CODEBOOK RESPONSE SHEET`. The questions marked as `mandatory, blocking` prevent the codebook response sheet from being saved until completed. The questions marked as `mandatory, non-blocking` get flagged in the UI but do not prevent the codebook response sheet from being saved until completed.

**EMPIRICAL FILES:** Each of the "empirical files" is essentially a catalogue entry for a plaintext, Markdown, or PDF file. Each empirical file can also be assigned a title, a date (e.g., date of interview, date of publication), and a custom ID (e.g., SF-2026-KXV-01) at the level of this catalogue. As mentioned above, each empirical file may have one or many codebooks associated.

**SELECTIONS:** A highlighted portion of text in an empirical file is a `SELECTION`.

- One or many selections can be tagged as _evidence for_ for an `OPEN CODE`.

- An open code has its own payload, including optional `comments` (an array of strings) and optional `questions` (also an array of strings, but representing unresolved matters from a qualitative/interpretivist/hermeneutic perspective).

- One or many open codes can be then tagged as _evidence for_ an `AXIAL CODE` which has the same optional payloads (comments, questions). One or many axial codes can also be tagged as _evidence for_ other axial codes. So basically open codes and axial codes are very similar, with the exception that open codes are those that are directly evidenced by selections.

- A special part of the payload of an open code or axial code is the researcher's commentary on the relationships between two or more selections tagged to it. Each of these is a `INTERRELATION`. Each interrelation can be classified against a user-defined list of interrelation types (but preload with the following options: Compare, Contrast). Each interrelation can also contain a text description.

- A selection can be marked as `irrelevant`. Per definition, no selection marked as `irrelevant` should ever be serving as evidence for an open code. If a selection is already selected serving as evidence for an open code, no part of it be marked as irrelevant. If a selection is already marked as irrelevant, no part of it can be included as a selection for serving as evidence for an open code.

**LAYERS:** The structure of selections (including marking as irrelevant), open coding and axial coding all exist in a "layer". This concept is adapted from the likes of Photoshop and GIMP.

- Many projects will only have one layer, which is quite fine. More advanced projects may introduce multiple layers (e.g., different theoretical lenses; different researchers' interpretations; etc.). Selections and coding are strictly not allowed to exist on more than one layer. Any selection or code can be transferred from one layer to another, but all associated selections and codes move it with as well.

- For any given project, the researcher can enable the "Interlocuter" layer. Here, the researcher can map the conversational turns in interview transcript to various interviewees and researchers (see below) based on simple text header lines, e.g.:

```
Alice Bob
I now like to ask you a little bit about the user interface for QDVC Empirics. Do you think it's user friendly?

John Smith:
Well, it's certainly an improvement over alternatives. The existing crop of QDA software is very limited. But I'm still getting used to the user interface of QDVC Empirics, to be honest.

ALICE BOB:
Which part of the user interface is taking the longest to get used to?

John Smith

Oh, that's a hard one. I can't remember off the top of my head. Is it okay if I pull it up on my laptop here?
```

(Notice the inconsistent capitalisation, use of `:`, and line breaks. These all need be handled gracefully.)

**INTERVIEWEES:** QDVC Empirics can optionally maintain a list of interviewees. Each interviewee has a first name, last name, and consent form (PDF file, but not listed as an empirical file). It is assumed that the first name and last name are pseudonyms; the UI should explicitly inform the researcher thusly.

**RESEARCHERS:** QDVC Empirics can also optionally maintain a list of researchers, each with a first name and last name (real names).

**DATA STORAGE:** Each project has two folders where the data is stored:

- Most of the project data is stored in a "workspace" folder and Git-tracked elsewhere. YAML is the preferred data structure, supplemented by CSV where it makes sense. This includes all codebooks, codebook response sheets, selections, open coding, axial coding, layers, and interviewee and research records. For data security reasons (human research ethics for interviews, intellectual property considerations for literature reviews), the project workspace folder does NOT include full-texts for the empirical files (e.g., interview transcripts, research article manuscripts) and it does NOT include PDF consent forms (if applicable).

- The sensitive files mentioned above (full-texts, consent forms) are stored in a "full-texts" folder to be accessed on a strictly read-only basis. The location of this full-texts folder is not stored in the project workspace folder; it is remembered per-project per-device, and that is something which can be erased from the app settings.
